# store-notes/ — the release note each storefront gets

Generated by `all/changelog.py` on every release (`all/run.sh` calls it with
`--store-notes-dir`), one file per storefront, each in that store's own format
at that store's own limit. Nothing here is written by hand; edit the text in the
store's own console at submission time, not in this tree, because the next
release overwrites these files.

Every file is **this app's own changes first, then the changes shared with the
other three apps**, separated by a boundary you can delete in one motion. The
shared half is real — the sdk and connect commits below the line are compiled
into the artifact that store serves — but whether it belongs in a consumer-facing
note is a judgement only the person submitting can make. Delete it or keep it.

| file | pasted into | limit | format |
| --- | --- | --- | --- |
| `apple/en-US/release_notes.txt` | App Store Connect → **What's New in This Version**, on both the iOS and the macOS version | 4,000 characters | plain text |
| `windows/en-US/whats_new.txt` | Partner Center → Store listings → *language* → **What's new in this version** | 1,500 characters | plain text |
| `linux/release-description.xml` | `urnetwork/linux` `app/packaging/com.bringyour.network.metainfo.xml.in` → `<releases><release><description>` | none | AppStream XML |

**Android is not here.** Its note lives at
`metadata/en-US/changelogs/<versionCode>.txt`, because that is the file F-Droid
reads directly off this repository (fdroiddata's `com.bringyour.network.yml`
carries `Repo: https://github.com/urnetwork/build`), and `all/run.sh` writes it
once per `FDROID_VERSION_CODE_OFFSETS` entry plus `default.txt`. The same text
is what a human pastes into the Play Console. A second copy under `store-notes/`
would be a second source of truth for the one note nobody reviews before it
ships, so there isn't one.

Nothing that is not an Android changelog may go under `metadata/`, either:
fdroidserver globs `build/[A-Za-z]*/metadata/[a-z][a-z]*` and then `os.walk()`s
it, matching changelog files by bare filename at any depth. A file dropped in
there would silently overwrite the real `en-US` note or invent a locale in the
F-Droid index. `store-notes/` is a sibling of `metadata/` and is invisible to
that glob.

## Deleting the shared half

**apple, windows** — plain text has no comment syntax, so the marker is text a
reader is allowed to see: a blank line, then `Under the hood`. Delete from the
blank line to the end of the file. If you forget, it publishes as a perfectly
ordinary release note rather than as a leaked machine marker, which is why it is
worded the way it is.

**linux** — XML comments are legal inside `<description>` and cost nothing
(`appstreamcli` only inspects element children; GNOME Software and KDE Discover
parse the XML and drop comments). Delete everything between

```xml
<!-- Shared with the other URnetwork apps. ... -->
<!-- end of the shared section -->
```

inclusive.

**android** — the boundary is a bare blank line and nothing more. 500 characters
is the whole budget on that store and a heading would cost a real bullet; the
generated note has measured 486/500 on a one-week span. Delete from the blank
line down when pasting into the Play Console. Do not delete it from the file:
that file is also what F-Droid publishes, unattended.

## Wiring the Linux fragment

`linux/release-description.xml` is the **children of `<description>`**, already
indented to sit at that depth — not a whole `<release>` element and not a
standalone document. `urnetwork/linux` consumes it by committing a
`app/packaging/release-description.xml` and reading it at configure time:

```meson
metainfo_xml = configure_file(
  input : 'packaging/com.bringyour.network.metainfo.xml.in',
  output : 'com.bringyour.network.metainfo.xml',
  configuration : {
    'APPSTREAM_VERSION' : _appver,
    'APPSTREAM_DATE' : _appdate,
    'APPSTREAM_RELEASE_DESCRIPTION' : fs.read('packaging/release-description.xml').strip(),
  },
)
```

It has to be a **committed file read by meson**, not a `-D` option: the Flatpak
is the only channel that installs the metainfo, and Flathub builds that manifest
on its own infrastructure where nothing in this pipeline runs — the same trap
`packaging/flatpak/com.bringyour.network.yml` already documents for
`-Dapp_version`.

Until that file exists in `urnetwork/linux`, `all/run.sh` says so and changes
nothing there. Once it does, every release refreshes it, carried by the same
`git add .` that already carries `app/po`.
